Secret Wards — offline de-identification for Indian hospital records

Track 3 submission brief · repository riddhimajaiswal18/Secret-Wards · branch feat/detection-release-pipeline · commit 3433e49+

Problem

Indian hospital data is heterogeneous: CSV billing exports, JSON patient indexes, FHIR bundles, XML discharge summaries, WhatsApp-style referral notes, scanned PDFs and photos. It mixes English, Devanagari and Hinglish, and it is full of numbers that look like identifiers but are clinical measurements. Deleting too much destroys research value; deleting too little exposes patients. A single missed phone number or a filename is enough to re-identify a person.

Solution

A deterministic, CPU-only, no-LLM pipeline that parses each format into one intermediate representation with source locations, decides what is identity and what is clinical, transforms in place, and then independently verifies the released bytes before anything is published.

Privacy strategy

  • Direct identifiers substituted, never pattern-preserved.
  • Role-aware: patient names removed, clinician names retained — proven necessary by measurement.
  • Every channel treated as a channel: content, filename, header, key, metadata, base64.
  • Quarantine is not a copy: unsupported content is declared, never silently dropped or released.
  • Determinism: same input + secret ⇒ byte-identical output; different secret ⇒ different output.
  • Release integrity: parsing success can never masquerade as sanitisation success.
  • Verification is independent of the detector, so one blind spot cannot approve itself.
  • No identity→pseudonym mapping is ever stored, so there is no envelope to protect.

Limitations and threat model

  • Not anonymity. Residual re-identification risk remains; quasi-identifier generalisation and date shifting are scoped but not yet implemented, and cross-hospital linkage is not shipped.
  • Names are the weak class. Name detection is heuristic and context-dependent; 557 verifier candidates are dominated by name-like strings, which are not yet triaged against a labelled set.
  • Scanned images. OCR depends on a rendering binary that is absent here; affected files are declared and quarantined rather than released uninspected.
  • Verification scope. The verifier checks identifier classes it knows in channels it can read; it is a release-safety layer, not a proof of anonymity.

Constraints and reproducibility

Offline, CPU-only; 2 vCPU / 4 GB / 15-minute budget; no LLM and no pretrained model above 50 M parameters; deterministic under a fixed secret. Reproduce with pip install -r requirements.txt, then python main.py --input <dir> --output <dir>; validate with the Team Kit validate_output.py (CONTRACT OK) and check_submission.py (READY TO SUBMIT), and gate a release with python tools/verify.py <input> <output>.
